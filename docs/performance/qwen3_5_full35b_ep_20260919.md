## Measurement

Each repeated arm runs 64 optimizer steps. The predeclared primary window is
steps **9-64**, including all 56 intervals, with no outlier removal. Wall time is
the difference of successive rank-0 completed-step timestamps; it includes the
next fetch, training, monitoring/logging and common measurement overhead.
The inherited harness synchronizes devices and reduces step elapsed time with
MAX across ranks. The separate compute column is the mean of these per-step
max-rank forward/backward/optimizer measurements, not the maximum of 64 steps.
Neither column is MFU or a kernel-only timing.

Timing runs do not enable the profiler. The four repeated arms run in OFF/ON/ON/OFF
order. Baseline phase diagnostics and unit tests occurred between the first OFF
and ON; there was no concurrent GPU benchmark or keeper. The last three arms ran
consecutively. These are measured repeats, not a statistical-significance proof.

The strict gate remains `abs(on-off) <= 1e-4 + 1e-3 * abs(off)` for every recorded
loss and gradient norm. All four arms actually match **exactly** at all 64 steps.
Their used FLA autotuner configurations also match on every rank, not just their
environment variables. This does not assert bytewise equality of every model
parameter at every optimizer step.

## Implemented changes

Local branch: `perf/issue-1038-full35b`. No push was requested or performed.
No patchgen-generated model file, training configuration, checkpoint or disabled
MoE numerical path was changed.

| Commit | Change | Correctness boundary |
|---|---|---|
| `b9b23ab` | Consolidate CUDA EP integer planning/validation on the CPU | Same IDs, counts, splits and checks; original CUDA result device |
| `93715f9` | Priority heaps and rank masks replace repeated full candidate sorting/scanning | Same complete priority key, tie breaks, slot policy and allocations |
| `ad4c485` | Reusable chunk row maps and a single copy/autograd boundary | Exact permutation/inverse, integer indexing widened before arithmetic |
| `d8576e6` | Fuse alias gather, BF16 weighting, ordered output sum and backward products | Logical accumulation order and BF16 rounding retained; original ATen weight-gradient sum |
| `4323191` | Skip provably non-improving first-replica targets | Only a two-rank first move is pruned; existing multi-rank replicas keep the original search |

The weighted-combine fast path is CUDA BF16, contiguous/aligned storage, supported
top-k and hidden widths divisible by 16, with bounded CUDA flat-grid size. It
supports first-order gradients. Other inputs retain the exact PyTorch fallback.
Review caught that moving an unaligned row can change ATen's vectorized reduction
head and therefore large-number cancellation; the guard and explicit H257
regression test were added before freezing the production comparison.

The pruning proof is narrow: without an existing replica, a positive integer
transfer between ranks whose load difference is at most one can only exchange
their loads or worsen the descending-sorted load profile. Later target ranks are
no lighter, so that expert's target scan can stop. Reallocations involving existing
replicas are deliberately not pruned by this condition.

Independent code review approved each commit. Final CPU related suite:
**149 passed / 75 skipped**. Weighted-combine GPU suite: **97 passed**, including
aligned cancellation, repeated execution, signed zero, frozen gradient inputs,
unsupported-width/storage fallback, empty shapes and a grid with 65,537 tokens.
Chunk-permutation GPU suite: 39 passed. CPU count-based tests compare complete
plans against the original scan, including exhaustive small integer histograms
and more than 64 ranks. NPU execution was not retested.

Same-state operator probes use all 40 layers on all eight ranks with actual
captured model inputs and pretrained expert weights. They compare output, input
gradient and routing-weight gradient against the reference. All 320 records pass;
the reference expert output also matches the recorded full-model expert output.
This is stronger than random input testing but still scoped to those samples.

Microbench observations, **not end-to-end gains**:

- Heap planner: old/new summed per-case max-rank time over 40 samples about
  168.45/106.10 ms.
- Initial fused chunk-permutation prototype: about 55.47/16.24 ms over 40 samples
  for one forward/backward permutation. Production additionally reuses maps.
- Weighted-combine production arithmetic before the conservative alignment gate:
  46.37/23.54 ms over 40 actual H2048 samples. The final gate retains this shape;
  the full-model repeated runs above use the reviewed guarded implementation.
- First-replica pruning: CPU-only 40-histogram mean over 20 alternating trials
  28.85/21.02 ms, with identical plans. This is not an eight-GPU step benchmark.

## Calibration, bottleneck evidence and limits

Earlier unprofiled 128-step calibration (steps 9-128) measured original OFF
2.347363 s, original ON 2.526887 s, and the chunk/heap snapshot ON 2.420437 s.
All 128 warm OFF/ON and chunk-snapshot loss/gradient-norm values matched exactly.
This shows the original enabled-path overhead and optimization direction, but
these earlier jobs are not additional repetitions of the final 64-step matrix.
The initial harness version lacked the later after-timing FLA configuration dump;
it is archived under `harness-v1/`. The final matrix uses identical V2 harnesses.

Balancing really executes: the 128-step chunk run's steps 9-128 have mean
normalized rank-load absolute deviation 0.413609 before and 0.039082 after,
mean moved-token fraction 0.219296, and mean 281.86 replica events across 40 layers
per step. More balanced tokens do not by themselves imply faster training.
The final pruning trial's primary window has deviation 0.489286 -> 0.040563,
moved fraction 0.259819 and mean 280.375 replica events across 40 layers per step.
Its complete 64-step EP telemetry matches the fusion version exactly.

The original full PyTorch traces have large profiler overhead: roughly 5.0-5.5 s
per captured step versus about 2.4 s normally. They contain millions of tiny
CPU/runtime events. Their inclusive times and overlapping GPU sums cannot be
added or transplanted directly into an unprofiled speedup estimate.

An additional unchanged-OFF, 16-step low-volume event diagnostic measured steps
12-13 at 2.384/2.401 s of max-rank compute, or 2.395389/2.413181 s of completed-step
wall time. It records exactly 84 ranges per rank: 40 text MLP forwards
and two vision Conv3d forwards per step. The two Conv3d forwards together cost
about **1.056-1.196 s of CPU submission time**, with current-stream intervals of
**1.015-1.183 s**. These ranges are across ranks after averaging each rank's two
measured steps, not extrema across all individual rank/step samples. All 40 text
MLP forwards sum to about 0.216-0.220 s of CPU time by the same averaging rule;
this excludes their backward and is not a total MoE time bound.
The diagnostic loss/gradient curves match the first 16 baseline steps exactly.

The shared vision cost is real, not solely profiler inflation. Full determinism
disables cuDNN in the existing helper, exposing the native slow Conv3d path for
patch embedding. Both ON and OFF retain it. No common Conv3d optimization,
cuDNN/config change, shorter model, altered data or recompute was used to improve
the ON/OFF comparison. Any future common-kernel gain must be reported separately
from the residual EP enablement benefit.

Evidence: `profile-verification/REPORT.md`, `results/initial-*-profile/`, and
`results/diagnostic-off-phases16/phases.rank*.json`. The diagnostic launch contains
the original reference arguments plus the actual modified 16-step command and
`diagnostic_only=true`; it is not an acceptance timing run.

The initial cold OFF profile had different FLA autotuner choices across ranks
and a different numerical curve from subsequent warm runs. A fresh warm OFF
run exactly matched warm ON, disproving an EP-only explanation for that initial
discrepancy. The cold result is retained, not silently discarded. This task does
not establish cross-cold-start determinism for unrestricted FLA autotuning.

as a demonstrated balancing speedup when no replicas execute.
